Antes y después: SOLID aplicado al backend

Comparación real, tomada del mismo proyecto, de cómo estaba el código antes de aplicar SOLID y cómo quedó después de refactorizarlo por capas. Cada bloque muestra el problema concreto, el código exacto de ambas versiones, y qué consecuencia práctica tenía uno vs. el otro.

Arquitectura

De rutas monolíticas a capas por módulo

Antes, cada archivo de routes/ hacía todo: validaba, aplicaba reglas de negocio y consultaba la base de datos en la misma función. Después, cada capacidad de negocio (listings, auth, admin...) se organizó en un módulo con 4 responsabilidades separadas, conectadas por un único punto de composición.

Antes

  C[Cliente HTTP] --> R["routes/listings.ts
validación + reglas de negocio + queries Drizzle, todo junto"]
  R --> DB[(Base de datos)]
Consecuencia:
  • Un solo archivo cambia por 3 razones distintas (SRP roto)
  • La regla de negocio queda escrita adentro de la consulta SQL, no se puede leer por separado
  • Cambiar de ORM implica tocar cada archivo de rutas

solo HTTP"]

reglas de negocio"]
  SV --> IF[["IListingsRepository
interfaz"]]
  IF -.implementa.- RP["listings.repository.ts
Drizzle"]
  RP --> DB[(Base de datos)]
  CT["container.ts
composition root"] -.inyecta.-> SV
  CT -.inyecta.-> RP
Consecuencia:
  • Cada capa cambia por una sola razón (SRP)
  • La regla de negocio queda escrita en una función con nombre propio, se lee sola
  • Cambiar de ORM solo afecta a *.repository.ts
Regla de dependencia: routes → service → interfaz del repositorio ← repositorio (implementación). El service nunca conoce la implementación concreta, solo la interfaz — eso es Inversión de Dependencias (DIP) puesta en la arquitectura.
SRP Alta cohesión

Bloque 1 — Editar un alojamiento (PATCH /listings/:id)

routes/listings.ts → modules/listings/*

Este endpoint es el ejemplo más claro: en una sola función se mezclaba validación de parámetros, una consulta para ver si existe, una regla de permisos, validación del body, transformación de datos y el UPDATE a la base de datos.

Antes routes/listings.ts
router.patch("/listings/:id", requireAuth, async (req, res) => {
  const user = (req as any).user;
  const id = parseInt(req.params.id, 10);

  // 1. validar parámetros
  const paramsParsed = UpdateListingParams.safeParse({ id });
  if (!paramsParsed.success || isNaN(id)) {
    res.status(400).json({ error: "ID inválido" }); return;
  }

    // 2. consultar directo a Drizzle para ver si existe
  const [existing] = await db.select().from(listingsTable)
    .where(eq(listingsTable.id, id)).limit(1);
  if (!existing) { res.status(404).json({ error: "No encontrado" }); return; }

    // 3. regla de negocio (permisos) mezclada aquí mismo
  if (existing.landlordId !== user.id && user.role !== "administrador") {
    res.status(403).json({ error: "No tienes permiso" }); return;
  }

  // 4. validar el body
  const parsed = UpdateListingBody.safeParse(req.body);
  if (!parsed.success) { res.status(400).json({ error: parsed.error.message }); return; }

  // 5. transformar los datos a mano
  const updates: any = {};
  if (parsed.data.title != null) updates.title = parsed.data.title;
  // ...7 líneas más igual de repetitivas...

    // 6. y finalmente, el UPDATE directo a Drizzle
  const [updated] = await db.update(listingsTable).set(updates)
    .where(eq(listingsTable.id, id)).returning();
  res.json(formatListing(updated));
});
Consecuencia real de esto:
  • La función tiene 3 razones distintas para cambiar: cambia el formato de la API, cambia la regla de quién puede editar, o cambia la forma de guardar en BD — y las tres tocan el mismo archivo.
  • La regla de permisos ("dueño o admin") está mezclada entre validaciones de HTTP y una consulta SQL, en vez de leerse como una sola idea.
  • Esta misma lógica de permisos estaba duplicada en el DELETE de abajo, letra por letra.
Después modules/listings/
listings.routes.ts — solo HTTP
router.patch("/listings/:id", requireAuth, async (req, res, next) => {
  try {
    const id = parseInt(String(req.params.id), 10);
    if (!UpdateListingParams.safeParse({ id }).success) {
      res.status(400).json({ error: "ID inválido" }); return;
    }
    const parsed = UpdateListingBody.safeParse(req.body);
    if (!parsed.success) {
      res.status(400).json({ error: parsed.error.message }); return;
    }
    res.json(await service.update((req as AuthenticatedRequest).user, id, parsed.data));
  } catch (error) { handleRouteError(error, req, res, next); }
});
listings.service.ts — la regla de negocio, aislada
async update(user: User, id: number, input: ListingUpdate) {
  const existing = await this.repository.findById(id);
  if (!existing) throw new HttpError(404, "Alojamiento no encontrado");
  if (existing.listing.landlordId !== user.id && user.role !== "administrador") {
    throw new HttpError(403, "No tienes permiso para editar este alojamiento");
  }
  const updated = await this.repository.update(id, input);
  return this.format(updated);
}
listings.repository.ts — el único que conoce Drizzle
async update(id: number, updates: ListingUpdate) {
  const [updated] = await db.update(listingsTable).set({ ...updates, updatedAt: new Date() })
    .where(eq(listingsTable.id, id)).returning();
  return updated;
}
Consecuencia real de esto:
  • La regla "solo el dueño o un admin puede editar" vive en un solo lugar (listings.service.ts) y ahora la reutiliza también el DELETE, sin copiar y pegar.
  • El service no sabe si los datos se guardan en Postgres, en otra base de datos o en un archivo — solo conoce los métodos de la interfaz.
  • La ruta ya no sabe que existe Drizzle; solo conoce al service.
DIP Bajo acoplamiento

Bloque 2 — Cómo se conectan las piezas (composition root)

routes/index.ts → container.ts

Antes no existía ningún punto donde se "armara" el sistema: cada router se importaba directo y usaba db internamente. Después existe un único archivo, container.ts, que crea los repositorios (implementaciones concretas) y se los inyecta a los services (que solo conocen la interfaz).

Antes routes/index.ts
import authRouter from "./auth";
import listingsRouter from "./listings";
// cada router se construye a sí mismo por dentro,
// importando `db` en su propio archivo

router.use(authRouter);
router.use(listingsRouter);
router.use(roommatesRouter);
Consecuencia:
  • listingsRouter trae su propia dependencia a Drizzle desde adentro; nada externo decide con qué implementación trabaja.
  • No existe un lugar único donde ver "de qué depende cada cosa" del sistema.
Después container.ts
const listingsRepository = new ListingsRepository();  // implementación concreta
const authRepository = new AuthRepository();

export const container = {
  listings: new ListingsService(listingsRepository),
  auth: new AuthService(authRepository),
  requireAuth: createRequireAuth(authRepository),
  requireRole: createRequireRole(authRepository),
};
// routes/index.ts
router.use(createAuthRouter(container.auth, container.requireAuth));
router.use(createListingsRouter(container.listings, container.requireAuth));
Consecuencia:
  • ListingsService recibe su repositorio por parámetro; no lo crea ni decide cuál usar, solo lo usa.
  • Un solo archivo (container.ts) muestra todo el mapa de dependencias del backend.

Bloque 3 — El middleware transversal requireAuth

middlewares/auth.ts

Este middleware se ejecuta antes de cada endpoint protegido: toma el token del header Authorization, lo valida, busca al usuario correspondiente y lo agrega a la petición (req.user) para que el controlador lo use. Al no pertenecer a ningún módulo de negocio en particular, es código transversal — corre igual para listings, auth, roommates, admin y dashboard.

Antes
import { db, usersTable } from "@workspace/db";
import { eq } from "drizzle-orm";

export async function requireAuth(req, res, next) {
  const payload = verifyToken(token);
  const [user] = await db.select().from(usersTable)
    .where(eq(usersTable.id, payload.userId)).limit(1);
  if (!user) { res.status(401).json(...); return; }
  req.user = user;
  next();
}
Consecuencia:
  • El middleware conoce el detalle de cómo se guarda un usuario en la base de datos (tabla usersTable, columna id), en vez de simplemente pedir "el usuario con este id".
  • La misma consulta ya existe como AuthRepository.findById(): la lógica de "buscar usuario por id" queda escrita dos veces en el proyecto.
Después
import type { IAuthRepository } from "../modules/auth/auth.repository.interface";

// fábrica: recibe la ABSTRACCIÓN, no `db`
export function createRequireAuth(repository: IAuthRepository) {
  return async function requireAuth(req, res, next) {
    const payload = verifyToken(token);
    const user = await repository.findById(payload.userId);
    if (!user) { res.status(401).json(...); return; }
    req.user = user;
    next();
  };
}
// container.ts — se arma UNA sola vez, con el mismo authRepository
requireAuth: createRequireAuth(authRepository),
Consecuencia:
  • El middleware pide "el usuario con este id" a través de IAuthRepository y no le importa si detrás hay Drizzle, otro ORM o cualquier otra fuente de datos.
  • Reutiliza AuthRepository.findById() en vez de tener la misma consulta escrita en dos archivos distintos.
Extra · robustez, no es SOLID

Un bonus que aparece en el mismo archivo: fail-fast en la configuración

middlewares/auth.ts

Esto no es un principio SOLID, pero es una práctica de robustez que vale la pena mostrar: cómo se define el secreto usado para firmar los tokens JWT.

Antes
const JWT_SECRET = process.env.SESSION_SECRET || "pvaru-secret-2026";
Consecuencia:
  • Si alguien olvida configurar la variable de entorno en producción, la app arranca igual usando un secreto público, visible en el propio código fuente.
  • Cualquiera que lea el repositorio puede firmar tokens válidos.
Después
const JWT_SECRET = process.env.SESSION_SECRET;

if (!JWT_SECRET) {
  throw new Error("SESSION_SECRET must be set. Refusing to start.");
}
Consecuencia:
  • Si falta la variable de entorno, el servidor no arranca — el error aparece de inmediato en el despliegue, no meses después como una brecha de seguridad.
  • Mismo patrón que ya usaba lib/db al validar DATABASE_URL: consistencia en todo el proyecto.
